一段客服会话常常需要同时回答几件事：应该退款还是换货，是否需要人工介入，工单是否紧急。它们读取相同历史，却对应不同选项。如果每个问题都单独提交，服务就需要反复处理相同输入。Flide 新论文围绕这类决策负载提出精确状态分叉，将共享上下文与问题分支放进一次执行，同时保留每个问题独立求值的语义。[论文原页](https://arxiv.org/abs/2610.42148)记录的首次提交时间是北京时间 10 月 31 日。

## 共享历史，保持问题之间的隔离

Flide 把一次请求看成树：历史是主干，各个问题是分支。物理执行时，它把 token 放到一个平坦流中，再用 GPU 上的依赖索引标明每个分支可以读取什么。ForkAttention 同时处理标准注意力和循环式 Gated DeltaNet 层，让问题从共享历史对应的状态出发。[论文](https://arxiv.org/html/2610.42148v1)证明的是精确算术下的独立执行等价性；浮点执行还涉及运算顺序。

这一区别会影响概率阈值。例如系统规定人工介入概率超过某值就升级工单，同一输入在不同负载下的微小数值变化也可能改变动作。项目因此提供可选的 `--batch-invariant` 模式，并通过 `--session-cache-gb` 为不断增长的 Agent 历史保留状态。开发者可以分别考虑跨步骤复用和跨批次确定性，而不必把两者混为同一个缓存开关。[官方项目页](https://flide.org/)列出了这些选项。

## 与已有前缀缓存怎样衔接

减少重复上下文计算是多个引擎共有的能力。vLLM 的前缀缓存按 token 和父块等信息计算哈希，在 KV 缓存管理器中查找已计算块，并通过引用计数管理复用与回收。因此，比较方案时应先确认请求是否已有缓存命中，再测剩余的调度、分支计算与状态恢复成本。[vLLM 官方设计](https://docs.vllm.ai/en/latest/design/prefix_caching/)还提供请求级 `cache_salt`，用于限定共享缓存的信任范围；性能实验需要同时保留业务要求的隔离设置。

SGLang 的 RadixAttention 则用基数树管理 token 序列到 KV 张量的映射，结合缓存感知调度和淘汰策略服务多次调用。其前端也能表达分叉、生成与合并控制流。[原始技术介绍](https://www.lmsys.org/blog/2024-01-17-sglang/)说明了这些机制。对于应用开发者，程序能表达多个分支，与底层如何保存和恢复模型内部状态，是两个需要分别确认的层次。

Flide 的具体选择是把决策问题及其共享状态直接交给引擎。调用方组织问题，运行时负责状态分叉；评估时除延迟外，还应检查每个选项的概率是否符合原先的独立请求契约。这样可以避免只记录最终分类相同，却忽略接近阈值的概率发生偏移。

## 从工单判断扩展到 Agent 控制

[接入文档](https://docs.flide.org/)使用 `/v1/systemone`，请求包含 `state` 和 `questions`，每项答案返回选项概率。文档提供 Qwen3.5、Gemma 4 与专用决策模型的接入入口，Open-Jev 适配器需要先合并成检查点。选型时可以先固定模型、输入和阈值，再替换执行服务，保留相同业务判断标准。

工单系统可以把紧急程度、处理动作和转人工判断放进同一请求，减少应用侧重复拼接历史。下一步是工作流路由：在工具结果返回后，围绕更新后的状态判断是否继续、换工具或结束。再往后，评估服务也可围绕同一条轨迹提出多项独立判定，分别记录概率和对应证据，方便追查是哪条规则触发动作。这些是接口形态带来的应用方向，需要结合各自数据选择模型和阈值。

接入验证可以从少量真实轨迹开始：保存逐题独立执行的概率，比较合并请求的数值差异，再改变问题数、历史长度和并发。随后测试缓存命中、淘汰和新一轮历史追加时的行为。对需要稳定阈值的流程，再开启确定性模式观察成本。这样得到的结果能够直接回答服务是否适合当前业务，也能把模型判断能力和引擎执行效果分开衡量。
